CVE-2026-109618 and CVE-2026-109619: PHP Vulnerable to Unauthenticated RCE Attacks

Introduction

On October 21, 2026, two critical remote code execution (RCE) vulnerabilities, CVE-2026-109618 and CVE-2026-109619, collectively referred to as “PHP2Shell,” were publicly disclosed. Both vulnerabilities carry a CVSS v4.0 score of 9.2 out of 10. The PHP security team has released emergency patches and strongly encouraged all PHP users to update immediately. These flaws reside in the PHP core language runtime and successful exploitation allows an unauthenticated remote attacker to achieve remote code execution on any server running a vulnerable version, potentially enabling unauthorized access, data theft, or further system compromise. Given PHP's pervasive deployment across web infrastructure globally - including applications like WordPress, Drupal, Joomla, and Magento, as well as embedded devices and similarly overlooked public-facing platforms - the attack surface is extraordinarily large. Critically, because exploitation requires no authentication and no user interaction, attacks can be fully automated and executed at internet scale with no preconditions. The potential for mass exploitation by both opportunistic and nation-state threat actors is therefore considered high.

ThreatLabz analysis indicates that attackers began rapidly targeting these vulnerabilities following public disclosure, highlighting the need for organizations to patch vulnerable PHP deployments immediately.

Zscaler’s security team has analyzed this issue across both production and corporate environments and has ruled out any impact to Zscaler Cloud Platforms, products, distributed components, services, or our enterprise environment, as detailed in the Trust post.

Recommendations

Organizations running PHP should take the following actions:

  1. Patch immediately: Upgrade PHP to one of the fixed versions: 8.5.12, 8.4.27, 8.3.36, or 8.2.35. Linux package maintainers received patches in advance and may already have updated packages available. PHP packages for most Linux distributions may also include the patches backported to previous versions of the software, so consult the release notes for your specific installation to ensure your systems are covered.
  2. Deactivate unpatched instances: Consider fully disabling services for any PHP instance that cannot be immediately patched. While this may seem overly cautious, any unpatched instance could be targeted by opportunistic adversaries and result in shell-level access to the vulnerable host. Disabling the service is the only way to ensure the security of the instance.
  3. Inventory PHP deployments: Conduct an immediate inventory of all PHP installations across your environment, including standalone servers, vendor appliances, bundled software (WordPress, Magento, WooCommerce, Shopware), and hosting panels (cPanel, Plesk, etc).
  4. Migrate off EOL branches: Organizations running PHP 5.4+, 7.x, 8.0, or 8.1 must migrate to a supported branch immediately. No official binary patches will be released for these versions.
  5. Isolate EOL instances that cannot be immediately migrated: Migrating EOL instances is strongly recommended. If this is not possible, isolating unpatchable applications from the internet and other untrusted networks may provide some level of protection. This should be considered a high-risk mitigation and reserved only for business and mission-critical applications while implementing aggressive monitoring of these instances.
  6. Monitor for exploitation: Audit web server logs (including but not limited to Apache, Nginx, etc.) for unusual segmentation faults, crash dumps, or abnormal memory usage patterns that may indicate active exploitation attempts.
  7. Mitigate risk through PHP settings: While not a definitive fix, mission critical applications that cannot be disabled or immediately patched may benefit from reviewing and tightening memory_limit and max_execution_time settings in php.ini to avoid triggering OOM conditions. Consult additional guidance regarding mitigations through setting session.upload_progress.enabled = Off and disabling multipart uploads at the service edge.


ThreatLabz observes widespread exploitation attempts within 48 hours

ThreatLabz observed scanning activity and possible exploitation attempts targeting the PHP2Shell vulnerabilities using multiple attack tools and exploitation methods, including RCE payloads, PHP object injection, and named exploitation frameworks, indicating rapid, widespread in-the-wild exploitation attempts.

In the first 48 hours after the PHP2Shell disclosure, Zscaler’s global decoy mesh observed 1,156 exploitation attempts from 156 unique attacker IPs targeting 70 organizations. As a rapid response measure, a new detection rule for PHP2Shell exploitation has been pushed to all Zscaler Deception customers.

Attack chain

Automated scanning activity observed by Zscaler suggests attackers may be attempting to use a two-stage PHP2Shell exploitation chain, as shown in the figure below.

Figure 1: Notional exploit chain consistent with scanning and exploit attempts observed by ThreatLabz.

Stage 1: State setup and fatal trigger

The attacker sends a crafted multipart/form-data POST request containing:

  1. A PHPSESSID field to associate the request with a known session, making the session filename (sess_[PHPSESSID]) predictable.
  2. The PHP_SESSION_UPLOAD_PROGRESS field to force PHP to begin session bookkeeping during multipart parsing, populating vulnerable global state pointers and writing attacker-controlled data into the session file.
  3. A file attachment whose filename= parameter contains either PHP code or a serialized object string.
  4. A body sized or structured to exhaust memory (CVE-2026-109618) or trigger a fatal error (CVE-2026-109619).

When the fatal condition is triggered, longjmp() aborts the request, freeing per-request memory but leaving stale global pointers.

Stage 2: Heap reclaim and code execution

The attacker immediately sends a second request to the same worker process. This second request contains the attacker's payload, sized and aligned to reclaim the freed memory slots. When PHP processes the new request and references the stale global state before re-initialization occurs, it reads and executes the attacker-controlled data, achieving arbitrary code execution with the privileges of the PHP worker process.

Zscaler Deception telemetry findings

ThreatLabz observed malicious POST requests targeting the PHP2Shell exploitation path across multiple tools and stages of the attack chain. Every observed request is a multipart/form-data POST targeting PHP endpoints, specifically /, /index.php, /api/endpoint.php, and /app/upload.php.

Exploitation payloads observed

1. ShellFlow PHP2Shell named exploit tool

The most forensically significant artifact is the presence of a multipart boundary string that explicitly names the exploitation tool. This indicator should not be considered durable, as an adversary can trivially replace the known strings with something less obvious. At this time, the ShellFlow tool uses a known boundary value, so it is a useful indicator for detecting the unmodified tool. The exploit tool request is shown below. 

POST / HTTP/1.1
Content-Type: multipart/form-data; boundary=----shellflow-php2shell

------shellflow-php2shell
Content-Disposition: form-data; name="PHPSESSID"

sf618_ec172709c8b74601
------shellflow-php2shell
Content-Disposition: form-data; name="PHP_SESSION_UPLOAD_PROGRESS"
shellflow_poc

------shellflow-php2shell
Content-Disposition: form-data; name="f"; filename="poc.bin"
Content-Type: application/octet-stream

AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA[...15485 bytes total...]

The multipart boundary shellflow-php2shell identifies the attacking tool by name. The poc.bin file body contains more than 15k bytes of data along with a repeated AAAA... characters, a characteristic heap spray pattern used for memory layout control in the CVE-2026-109618 OOM corruption path.

Notable characteristics:

  • The boundary string shellflow-php2shell directly identifies the ShellFlow PHP2Shell attacking tool, which is publicly linked to CVE-2026-109618 scanning activity.
  • The session ID sf618_ec172709c8b74601 contains sf618, possibly reflecting a developer’s shorthand reference to ShellFlow + CVE-2026-109618.
  • The application/octet-stream upload with a repeating AAAAA... buffer is consistent with a heap spray technique used to influence the memory layout when the OOM condition is triggered.

2. Active system() command execution payload

These requests represent the highest-fidelity indication of automated exploitation attempts. The filename= field contains a fully formed PHP webshell instruction designed to be written into the PHP session file through the session.upload_progress handler and later executed, as shown in the example below.

The filename= value [?php system('echo 'exploited digga' > pwned.txt');echo 'RCE';?] instructs the PHP runtime to:

  1. Execute the OS command echo 'exploited digga' > pwned.txt, writing a proof-of-compromise marker to disk.
  2. Echo the string RCE in the HTTP response body, providing an indication of successful code execution to the attacker. The RCE string may still be returned even if the preceding echo redirection fails.

This payload pattern was observed in two separate requests with identical content, consistent with automated retry behavior commonly seen in exploit frameworks.

3. PHP object injection via pipe delimiter

ThreatLabz also observed a PHP object injection request that abuses the session pipe delimiter, as shown in the example. The filename x|O:8:"stdClass":0:{} uses the PHP default session serialization format, where the | character separates a variable name from its serialized value.

POST /app/upload.php HTTP/1.1
Content-Type: multipart/form-data; boundary=--NeoMM2026
--NeoMM2026
Content-Disposition: form-data; name="PHPSESSID"
neosc4n00000000000000002
--NeoMM2026
Content-Disposition: form-data; name="PHP_SESSION_UPLOAD_PROGRESS"
neo_obj_inject
--NeoMM2026
Content-Disposition: form-data; name="f"; filename="x|O:8:\"stdClass\":0:{}"
Content-Type: text/plain
Z
--NeoMM2026--

How It Works

Both vulnerabilities are use-after-free memory safety flaws in PHP's core request-handling engine. All PHP applications are affected regardless of application-level security controls. The vulnerabilities can allow unauthenticated attackers to execute code on affected servers or read sensitive process memory; that memory may contain passwords, authentication tokens, API keys and certificates belonging to other requests or the server itself.

CVE-2026-109618: OOM Corruption / Uninitialized Memory Use

  • CVSS v4.0: 9.2 - Critical

  • Root Cause: PHP uses longjmp() to abort a request when it hits its configured memory limit. When a web application receives form input, PHP records new entries in its internal POST data structure before finishing their initialization. If an out-of-memory (OOM) error fires while internal request data is only partially initialized, longjmp() bypasses normal control flow, leaving memory in an inconsistent/uninitialized state. During request cleanup, PHP misinterprets this invalid data as valid and follows an attacker-controlled code pointer, yielding control of execution.

  • Exploit Vector: An attacker can intentionally trigger specific OOM conditions (e.g., via large memory allocations, deeply recursive calls, or maliciously crafted request payloads) to corrupt state and achieve unauthenticated RCE.

  • Impact: Unauthenticated Remote Code Execution

CVE-2026-109619: Use-After-Free / Stale Memory Access

  • CVSS v4.0: 9.2 - Critical

  • Root Cause: When PHP encounters a fatal error and calls zend_bailout() (via longjmp()), request-owned internal state can survive in global memory after its backing allocation has been freed. PHP workers process multiple requests in sequence, and certain internal pointers persist between requests. If a request crashes or exhausts memory at the right moment, those pointers are left pointing to already-recycled memory. A subsequent request processed by the same worker may access this stale memory before re-initialization occurs.

  • Exploit Vector: This vulnerability is chainable with CVE-2026-109618. The partial initialization in CVE-2026-109618 allows an attacker to shape the freed memory contents and gain control of the instruction pointer, enabling highly reliable RCE. Chaining these two CVEs requires no authentication and no user interaction.

  • Impact: Unauthenticated Remote Code Execution and memory/credential disclosure

Conclusion

PHP2Shell represents one of the most significant PHP vulnerabilities disclosed in recent years, given both the technical severity of the flaws and the unprecedented scale of the affected install base. The combination of CVE-2026-109618 and CVE-2026-109619 provides a reliable, unauthenticated path to full server compromise with no user interaction required.

Organizations are strongly urged to treat this as an emergency patching event. Systems running EOL PHP branches must be migrated without delay. Where patching cannot be completed immediately, network-layer controls should be applied as an interim measure.

ThreatLabz will continue to monitor active exploitation campaigns and update Zscaler platform protections as new indicators emerge.

How Zscaler Can Help

The following table shows the typical attack stages and the mitigations recommended by Zscaler.

  • Identify and fix any vulnerable PHP applications with Zscaler Exposure Management
