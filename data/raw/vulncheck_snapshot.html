PHP2Shell Vulnerabilities: CVE-2026-109618 and CVE-2026-109619

cveinitial-accessvuln-intelcanary

VulnCheck In the Wild: Join our research team on October 28 at 1 PM ET for a deep dive on exploiting PHP2Shell.

News of two impending critical RCE vulnerabilities (CVE-2026-109618 and CVE-2026-109619) in PHP prompted a huge, global overnight effort on Tuesday, October 20 when word of the vulnerabilities' existence leaked ahead of the planned patch release. The PHP team confirmed an upcoming security release shortly after the leak occurred. Naturally, upon seeing the leaked info, ten thousand LLMs were immediately pointed at PHP source code.

On October 21, PHP published vulnerability details on what the community inevitably christened "PHP2shell":

  • CVE-2026-109618: RCE via OOM corruption (GHSA-w8hw-w9fx-j79w). Out-of-memory handling can interrupt PHP while internal request data is only partially initialized. Request cleanup may then treat the invalid data as valid.
  • CVE-2026-109619: RCE via stale global state (GHSA-6wmf-4rv5-p3rp). Request-owned internal state can survive after its backing memory has been freed. A later request handled by the same worker may use that stale state before normal initialization resets it.

VulnCheck research observations

The VulnCheck research team independently reproduced CVE-2026-109618 and CVE-2026-109619 late the evening of October 20. The team's early analysis was that the vulnerabilities can be exploited for RCE successfully on ARM64 systems and x86 systems without ASLR.

VulnCheck exploit availability: As of 1:30 AM ET on Thursday, October 22, the VulnCheck team had a weaponized exploit for CVE-2026-109618 available to Initial Access Intelligence customers, along with a dozen+ network rules. Our initial exploit leveraged a VulnCheck-discovered memory leak chained into RCE on PHP 8.4.26 on x86-64 platforms with ASLR enabled and display_errors=off, the recommended production configuration. As of 5:30 PM ET on Friday, October 23, the team's exploit supports:

  • PHP 8.4.10 through 8.4.26 on AMD64 and ARM64 with default settings and display_errors=off (mod_php)
  • PHP 8.5.10 and 8.5.11 on AMD64 and ARM64 with default settings and display_errors=off (mod_php)
  • WordPress exploitation on default Docker installs running the supported versions of PHP above

We are not aware of any other public or commercial exploit that achieves RCE on multiple versions of PHP in production configurations, though we expect that to change as adversaries and researchers develop incrementally more sophisticated attacks.

Hundreds of proof-of-concept repos have flooded GitHub, which our team is reviewing as they come in. Only a very small number have been legitimate exploits, but as of 7 PM ET on October 22, we've identified at least one PoC that successfully bypassed ASLR on x86-64 systems for a single version of PHP (8.4.26) with default heap configurations. In our team's testing, the PoC did not work outside of this specific setup.

We expect to continue seeing widespread exploit attempts with public PoCs, irrespective of whether the PoC code is functional or the target is exploitable. VulnCheck-reviewed GitHub exploits are available to the community in our XDB.

Mitigation guidance

The fixed versions are PHP 8.5.12, 8.4.27, 8.3.36 and 8.2.35. PHP 8.1 and older no longer receive supplier-provided patches. PHP's suggested mitigations for those who cannot apply patches immediately are in the advisory and reproduced below:

RCE via OOM corruption (CVE-2026-109618)

Set memory_limit=-1, preferably in a way applications can't override, such as php_admin_value in the FPM pool or Apache configuration, and check that no pool, directory or application setting puts a finite limit back. This removes the controllable PHP memory limit failure, but an underlying allocation failure can still reach the vulnerable path.

Set a low post_max_size. For applications that don't require file uploads, set post_max_size = 8M. If file uploads are necessary, set post_max_size = 32M. Keep upload_max_filesize below post_max_size. Consider enforcing limits at the web server or proxy level for decoded request size, input field count, multipart part count, header count, and nesting depth. These limits must also cover requests without a usable Content-Length.

Use a container or cgroup limit as an availability boundary, preferably with a policy that kills only the affected worker. Do not substitute RLIMIT_AS or RLIMIT_DATA, as these can cause the vulnerable allocation failure.

RCE via stale global state (CVE-2026-109619)

Set session.upload_progress.enabled=0 and restart every worker. Use php.ini, an FPM pool or server configuration that applies before request parsing. Do not rely on ini_set() or FPM .user.ini. This blocks the confirmed session paths but not other variants.

On PHP 8.5, set fatal_error_backtraces=0 and restart every worker. This blocks the confirmed fatal backtrace path only. Remove invalid or deprecated settings applied per request that emit diagnostics before initialization. Hiding diagnostics with error_reporting, display_errors or @ does not help.

Fix attacker-reachable fatal errors and execution timeouts, including failures in callbacks, upload or import processing and cleanup.

VulnCheck Canary Observations

VulnCheck Canary Intelligence recorded early behavior from two source IPs with the user-agent php2shell-scan/109618, which sent multipart file upload requests to index.php on hosts in several cloud regions and providers. The behavior observed appears to target CVE-2026-109618, the upload-progress vulnerability, where a multipart POST to any PHP endpoint that is processed by upload-progress can cause a memory limit failure. The scanning tool indicated in the user-agent references the same CVE number and the multipart upload requests utilize the upload-progress code path. For the IP addresses sharing the user-agent, our Canary hosts say two files named a and b are uploaded, but in this case was not enough to force memory exhaustion in one request.

We’ve also observed at least one attempted exploit from a China-based IP which tried to (unsuccessfully) drop a webshell via a server-side session file. It tried to read the file back through a file disclosure path, but the path did not exist, so the attempt received a 404.

PHP on the internet: VulnCheck Target Intel observations

VulnCheck Target Intelligence has identified PHP on 2,608,039 internet-facing hosts. That is 1.86% of the roughly 140 million IP addresses we saw responding on web protocols in the last 30 days. Based on the version information visible to us, we believe 2,607,985 of them (99.998%) are vulnerable or likely vulnerable to PHP2Shell.

The internet-facing target population splits fairly evenly:

  • 1,474,985 hosts (56.56%) advertise a PHP version below the fixed build for their branch.
  • 1,133,000 hosts (43.44%) run PHP but don't expose a version. We're treating these as versionless and are likely vulnerable, given how recent the CVE is. The fixed releases are only hours old, so there’s little reason to assume otherwise.

Patching has already started, if slowly. We see patching is beginning with some hosts on a fixed build (8.5.12, 8.4.27, 8.3.36 or 8.2.35).

Notably, a large share of the vulnerable population is on branches that PHP no longer supports:

  • 700,000+ hosts (27% of PHP hosts) run PHP 3.x through 7.3. These branches are end-of-life and won't receive a fix. PHP 7.4.33, the final 7.x release and still the single most common version we see, is on 172,000+ hosts.
  • Just under 400,000 hosts (15%) run PHP 7.4, 8.0 or 8.1. These are also end-of-life. The PHP security team has published source backports for them, but no new release, so they stay x exposed until someone rebuilds PHP by hand.

Taken together, 1.1 million+ hosts, about 42% of everything running PHP, are on end-of-life branches with no official patched release. For comparison, 403,000 hosts sit on the supported 8.2 through 8.5 branches and can upgrade more simply.

How PHP was found

Most of these hosts tell us they run PHP. 2,146,053 hosts (82%) identify it directly in their HTTP responses, typically through the X-Powered-By header or a cookie. The other 462,000 hosts (17.71%) never mention it because they run an application built on it.

Across the roughly 106 million hosts we see serving HTTP, PHP appears on 2.45%. Hosts that identify PHP directly make up 2.02%, and hosts found only through an application make up another 0.43%.
